# 배치기 설계 노트 — 앞단 출력만으로 배치하기

배치기 본체는 저장소 루트의 `src/*.mjs` 다 (의존성 없는 ES 모듈, 빌드 단계 없음, node 와
브라우저에서 같은 파일이 돈다). 이 폴더에는 검사(`test/`)와 고정값(`fixtures/`), 예제를 묶는
도구(`pack-example.mjs`)가 있다. 이 문서는 배치기가 **왜 이렇게 생겼는지**를 적는다 —
쓰는 법과 측정치는 루트 README, 검사 목록은 `symplace/README.md`.

```
src/linalg.mjs     행 우선 조밀행렬, Gram-Schmidt, 작은 선형계 풀이
src/subspace.mjs   제약 -> A z = b, 영공간 z = z0 + N theta
src/energy.mjs     매끄러운 HPWL(핀 경계) + 밀도(랭크 N) + 경계 벌점, 해석적 기울기
src/solver.mjs     Adam(이어붙이기 가능), 다중 시작점, variant 배정 탐색(라운드), 반전 고르기, 점수
src/lp.mjs         2단계 원시 심플렉스 (Bland 규칙)
src/legalize.mjs   theta 공간 legalization — 겹침을 정확히 0 으로, 배선 격자 정수 제약
src/design.mjs     1_topology + 2_primitives -> 배치 문제. variant/영역/반전의 자유도
src/place.mjs      입구 하나. 계층까지 엮어 앞단 출력 -> 배치 결과
src/job.mjs        배치 한 판 (워커에서도 메인 스레드에서도 같은 코드)
src/gpu/runner.mjs 연속 단계(Adam)를 WebGPU 컴퓨트 셰이더로
```

배치기를 쓰는 가장 짧은 길:

```js
import { placeHierarchy } from "./src/place.mjs";
const r = await placeHierarchy({ topology, primitives, templates });
//  topology   1_topology/<top>.verilog.json
//  primitives 2_primitives/__primitives__.json
//  templates  { concrete 이름: {bbox, terminals} }  (핀만 있어도 된다)
r.top.names / concrete / cx / cy / w / h / sx / sy / box / area / hpwl
```

`concrete` 가 **우리가 고른 variant**, `sx`/`sy` 가 **우리가 고른 거울 반전**이다.
둘 다 예전에는 ALIGN 배치기에서 받아 오던 것이다.

## variant 선택 — ALIGN 의 place 단계 없이

**요약: ALIGN 배치기 없이 앞단 출력만으로 배치한다.**
예전에는 블록 크기·핀·영역을 ALIGN 의 place 단계 출력에서 읽었다. 거기엔
ALIGN 이 이미 고른 답이 박혀 있었다. 지금은 `2_primitives` 에서 읽고
**우리가 고른다**.

### variant 가 뭔가

`2_primitives` 는 같은 소자를 여러 종횡비로 만들어 둔다. 트랜지스터도
파라미터도 같고 단위 셀을 몇 열 x 몇 행으로 깔았느냐만 다르다.

```
CMC_PMOS_51983143   X1_Y2    800 x 3528    1열 2행 (홀쭉)
                    X2_Y1   1120 x 2352    2열 1행 (넓적)
DP_NMOS_B_44742353  X1_Y3    800 x 4704
                    X3_Y1   1440 x 2352
```

면적은 비슷한데 **모양이 다르다**. 그래서 장식이 아니라 배치 문제의 일부다 —
홀쭉한 것들을 세로로 쌓는 것과 넓적한 것들을 가로로 붙이는 것은 전혀 다른
레이아웃이고, 영역 종횡비·대칭축 위치·배선길이가 전부 따라 바뀐다.
**연속 최적화로는 못 정하는 이산 선택**이다.

ALIGN 은 이걸 수열쌍 담금질 안에서 좌표와 같이 골랐다 (`sp.selected[block_id]`).
그 배치기는 ILP 솔버가 필요해 브라우저에 못 싣는다.

### 왜 어렵지 않은가 — 세어봤다

최상위 기준 variant 조합 (계층 설계는 하위 모듈이 올린 모양까지):

| 예제 | 블록 | variant 조합 |
|---|---|---|
| current_mirror_ota | 5 | **2** |
| five_transistor_ota | 3 | **60** |
| telescopic_ota | 5 | **8** |
| cascode_current_mirror_ota | 11 | **16** |
| high_speed_comparator | 10 | **108** |

블록이 11 개여도 조합은 16 개다. 대부분의 인스턴스는 variant 가 하나뿐이다.
**128 개까지는 전수, 그보다 크면 추첨**으로 덮을 수 있는 규모다.

### 어떻게 고르나 — 다중 시작에 얹었다

이미 시작점을 수십~수천 개 굴려 점수로 고르고 있으므로, 배정을 그 추첨의
한 축으로 넣으면 끝난다.

```
설정 = (variant 배정) x (영역 후보)
설정마다 A z = b 와 영공간을 새로 만든다   <- 대칭 계가 블록 크기에 의존한다
1 라운드는 설정마다 시작점 하나, 그 뒤는 점수 상위 설정에만 더 준다 (루트 README "예산은 라운드로")
상위 후보를 legalize 하고, legalize 뒤에 다시 점수를 낸다
```

**대칭 쌍은 묶인다.** `SymmetricBlocks` 의 2 원소 쌍은 서로 거울상이라 같은
variant 를 써야 한다 — 모양이 다르면 거울이 아니다. 홑원소(자기대칭)는 자유다.
그래서 선택 단위는 블록이 아니라 **그룹**이다 (`variantGroups`).

### 점수 — 로그 꼴, 핀은 경계 사각형

점수는 `log(면적) + w x log(HPWL) + 3 x 겹침` 이다 (`solver.mjs` 의 `scoreOf`). ALIGN 배치기의
비용 `log(area) + LAMBDA x log(HPWL_extend)` 와 같은 꼴이고 `w = 1` 이 ALIGN 의 `LAMBDA = 1` 이다.
로그라 기준값이 없다 — 면적 10% 와 배선 10% 가 같은 값이다.

HPWL 은 넷마다 **핀 경계 사각형**의 min/max 로 잰다 (ALIGN 의 `HPWL_extend` 와 같은 자). 핀을 점으로
재면 손가락 16 개를 한 줄로 늘어놓은 `X16_Y1` (핀이 폭 5,032 짜리 막대)이 공짜로 보여 길쭉한 variant 를
고르게 된다 — five_transistor_ota 에서 그렇게 골랐던 배정이 경계로 재면 배선이 2.1 배였다.
`test/variants.mjs` 가 배정을 전수로 돌려 줄 세운다 (점수 폭 telescopic 0.67 / current_mirror 0.39 /
five_transistor 2.87 — 0 이면 variant 선택이 무의미하다는 뜻인데, 최악과 최선의 차이가 e^2.87 배다).
분석 기록은 `symplace/PLAN-place-variants-gpu.md`.

**예전 점수(`면적/refArea + w x HPWL/refHpwl`)에서 두 번 틀렸던 것.** ref 를 배정마다 그 배정의
블록 합계 면적으로 잡으면, 같은 소자인데 variant 에 따라 블록 면적이 2 배 다른 경우
(`NMOS_4T_85599263`: X1_Y16 12.79M 대 X8_Y2 6.21M) 둘 다 빈틈없이 놓이면 점수가 같아져 **실리콘을
두 배 쓴다는 걸 점수가 못 본다.** 후보 집합의 최소값으로 정규화해도 같은 맹점이 돌아온다. 로그 점수는
기준값 자체가 없어 이 문제가 사라졌다.

### `Order` 는 부등식이라 legalize 로 간다

`Order`(블록을 주어진 순서대로 늘어놓기)는 등식이 아니라 부등식이라 영공간
매개화에 못 넣는다. 대신 legalize 가 **이미 쌍마다 분리 방향(왼/오/아래/위)을
고르고 있으므로**, 그 선택을 연속해에서 읽는 대신 제약이 정해주게 하면 된다
(`orderDirections` -> `chooseDirections(.., forced)`). 새 솔버도 새 변수도 없다.

순서는 추이적이라 이웃 쌍만이 아니라 모든 쌍을 박는다. 박은 방향이 실현
불가능하면 조용히 무시하지 않고 `NODIRECTION` 으로 실패시킨다 — 무시하면
제약을 어긴 배치가 그대로 나간다.

`high_speed_comparator` 가 `Order(X_MN0, XDP, XCCN, XCCP, top_to_bottom)` 을
건다. 넣어보니 **위반 0 건, 면적·HPWL 은 그대로**였다 — 연속해가 이미 순서를
지키고 있었다. 숫자는 안 움직였지만 이제 보장된다.
(`abut: true` 는 아직 안 다룬다. 그건 분리 부등식이 아니라 등식이라 영공간 쪽 일이다.)

### 거울 반전(sX, sY)도 같이 고른다

블록은 자기 중심에 대해 뒤집힐 수 있다. 크기는 안 변하고 **핀 위치만** 바뀌므로
영공간도 밀도도 면적도 그대로고 배선길이만 달라진다. variant 와 같은 종류의
이산 선택인데 훨씬 싸다 — 좌표가 정해진 뒤 좌표하강으로 고른다.

자유도는 제약이 정해준다. 세로축 대칭 아래서:

| | x 반전 | y 반전 |
|---|---|---|
| 자기대칭 (홑원소) | 고정 (블록이 이미 x 대칭) | 자유 |
| 거울 쌍 (A, B) | 한 비트, `sX_B = -sX_A` | 한 비트, 둘이 같아야 함 |
| 대칭 밖 블록 | 자유 | 자유 |

효과는 작지 않다 — 핀 경계로 잰 HPWL 이 **0.70 ~ 0.84 배**로 준다 (`test/place.mjs` 의
"반전 고르기 전 -> 후"). 후보의 점수도 반전 뒤의 HPWL 로 매긴다 — 반전 전 값으로 줄을
세우면 그 이득이 후보마다 다르게 붙어 순위가 흔들린다.

### 영역은 어디서 오나

place 단계 출력을 안 읽으니 "영역"도 우리가 정해야 한다. 세 군데서 온다.

1. **`AspectRatio` 제약** — 있으면 그게 정답 범위다. cascode 가
   `ratio_low 0.5 / ratio_high 2` 를 건다 (ALIGN 도 이걸 `PlacementCoreAspectRatio_ILP`
   전용 ILP 로 푼다).
2. **구조 힌트** — 두 제약을 함께 본다.
   - `Align h_*` 은 블록을 **가로줄**로 묶는다 (같은 y 선 = 옆으로 늘어선다).
     줄 안에서는 폭이 더해지고 높이는 하나다. 이 줄이 쌓기의 **단위**다.
   - `SymmetricBlocks(V)` 의 홑원소는 중심이 전부 같은 세로축 위에 놓여
     x 로 반드시 겹치므로 y 로 쌓인다: `W >= max`, `H >= sum` — 단, 블록이
     아니라 **단위**를 쌓는다. **거울 쌍은 쌓이지 않는다** (축 좌우로 벌어져
     나란히 설 수 있으므로 폭에만 기여).

   high_speed_comparator 에서 이게 결정적이다. 블록 단위로 쌓던 예전 식은
   2560x25872 (ar 0.099) 를 냈다 — 사다리(x1, x2, x4)가 6080 폭짜리 답에 닿지도 못했다.
   줄 단위로 고치니 6080x10584 가 나온다.
3. **면적** — 블록 합계 면적 x slack 이상.

힌트의 종횡비에서 출발해 **넓히는 쪽으로만** 사다리(x1, x2, x4)를 놓는다.
힌트는 "다 쌓인다"고 가정하므로 높이는 늘 과대평가, 폭은 과소평가이기 때문이다.

### 계층 설계 — 하위 모듈도 **여러 모양**으로 올린다

`high_speed_comparator` 와 `cascode_current_mirror_ota` 는 최상위가 하위 모듈을
인스턴스로 쓴다. 아래에서 위로 배치한다 — 하위 모듈을 먼저 배치해 크기와 포트
위치를 굳히고(`synthesizeTemplate`), 상위는 그걸 블록 하나로 본다.
굳힌 결과는 `2_primitives/<concrete>.json` 과 **같은 모양**이라 상위 모듈은
leaf 인지 하위 모듈인지 구분하지 않는다. ALIGN 도 같은 순서다.

**하위 모듈을 하나로 굳혀 올리면 상위가 그 모양에 갇힌다.** 실측 (hsc 의 하위 모듈 셋을 하나씩만
올리던 때): 2240x5880 (ar 0.38), 2240x3528 (0.63), 1600x3528 (0.45) — 전부 홀쭉했다. 하위 모듈의
점수에는 종횡비가 없기 때문이다 — 면적과 배선만 본다. 그런데 하위 모듈에서는 모양이 곧 상위의
입력이고, 그게 최상위 구조 하한을 4800x15288 (ar 0.31) 로 만든다.

고치는 방법은 점수에 종횡비 벌점을 넣는 게 아니라 **고르지 않는 것**이다.
하위 모듈의 점수는 그 모듈 자신의 면적과 내부 배선만 본다 — 상위가 어떻게
쓸지는 **그 자리에서 판단할 수 없다**. 판단할 수 있는 건 상위다. 그러니
고르지 말고 넘겨야 한다. 종횡비별로 몇 개(`SUB_VARIANTS`, 기본 3) 내어 상위의
**variant**로 등록하면 이미 있는 variant 선택 기계가 그대로 고른다.

**넘길 때 "좋은 것"을 고르면 안 된다 — "서로 다른 것"을 골라야 한다.**
여기서 두 번 틀렸다.

1. `alternatives` 를 **점수 순으로 잘랐다.** 그러면 종횡비가 한쪽으로 쏠린다.
   `PRIMITIVE_98739713` 의 점수 상위 3 개가 0.63 / 0.27 / 0.37 로 전부 홀쭉했고,
   넓적한 1.50 은 4 위라 **상위가 평가할 기회조차 없었다.**
   -> `spreadShapes` 로 종횡비 범위를 고르게 덮는다 (양 끝 + 점수 최선 보장).

2. legalize 를 **연속단계 점수 상위 N 개에만** 돌렸다. 예산이 늘면 후보 풀은
   커지는데 N 은 고정이라 잘 수렴한 것들끼리 몰려 **모양 자체가 줄어든다.**
   -> legalize 예산을 **반은 깊이(점수 상위), 반은 너비(설정마다 하나씩)** 로
   나눈다. 모양은 영역 후보가 정하므로 설정을 고루 훑으면 퍼진다.
   너비만 쓰면 반대로 손해다 — 평면 설계에는 모양 다양성이 필요 없고 점수 상위가
   밀려나는 손해만 남는다. 반씩 쓰면 둘 다 지킨다.

variant 선택은 여전히 모듈마다 따로 일어난다. 전 계층을 한꺼번에 최적화하지는
않는다 — 다만 하위가 여러 모양을 올리므로 상위가 그중에서 고를 수 있다. 하위 모듈이
올리는 모양이 3 개뿐이라 더 나은 모양이 상위에 오지 못하는 일이 아직 있다 (hsc 의
bbox 가 한 줄(2352) 높게 나오는 것이 거기서 온다).

### high_speed_comparator 를 파본 기록 — 짚었던 것이 셋 다 아니었다

처음엔 `Order` 제약을 무시해서라고 짚었다. **틀렸다.** 순서대로 재봤다.

1. `Align` 을 구조 힌트에 반영 -> 하한이 6080x10584 로 잡힌다.
2. 그런데 그 종횡비를 **직접 먹였더니 legalize 가 전부 실패**했다. 영역만의
   문제가 아니다.
3. legalize 실패 73/96 을 뜯어보니 방향이 아예 없는 쌍(`NODIRECTION`)은 **0 건**.
   각 쌍은 갈 곳이 있는데 **조합**이 안 맞는다 — MILP 를 LP 로 줄인 대가다.
4. 우리가 배치한 **하위 모듈**이 전부 폭 1280 으로 홀쭉했다. 그게 위층 입력이다.
5. 그 모듈을 뜯어보니 **배치는 완벽했다** (블록 2 개가 빈틈없이 나란히,
   채움률 1.00). 틀린 건 **variant 선택**이었고, 원인은 점수 정규화였다
   (위 "점수" 절).
6. 그 다음 (3) 을 하려다가 먼저 재봤다. **후보 96 개를 전부 legalize 해서
   절대 최선을 골라도 상위 16 개만 본 것과 똑같았다.** legalize 실패는 hsc 의
   병목이 아니었다. (cascode 는 반대였다 — 실패한 후보를 여유 영역을 넓혀 다시
   풀게 하니 34/34 가 풀리고 면적이 1.111x 에서 1.000x 로 갔다. 같은 처방이 아니다.)

교훈: 원인을 짚었으면 고치기 전에 재라. 여기서 세 번 틀렸다 —
`Order` 도, legalize 실패도, 영역 종횡비도 각각은 사실이었지만 병목이 아니었다.

## 검증

**parity** — 첫 구현(파이썬/numpy, 지금은 걷어냈다)이 뽑아 둔 `z0`/`N`/`lam`/`mu` 를
그대로 써서 같은 매개화 위에서 대조. 예제 4 개(3~11 블록) x 각 3 케이스, 전 항목 기계 정밀도.

```
중심 cx/cy   ~1e-16      배선 W    ~1e-16     밀도 D   ~1e-15
경계 B       ~1e-16      에너지 E  ~1e-16     기울기   ~1e-16
면적 A       ~1e-16      box       ~1e-16     overflow ~1e-16
유한차분 자체검증  ~1e-9
```

영공간 기저는 유일하지 않으므로(같은 부분공간의 아무 정규직교 기저나 된다)
JS 가 스스로 만든 N 은 값이 아니라 성질로 확인한다:
`A(z0 + N theta) = b`(임의 theta), `N^T N = I`, `dim = n - rank`. 전부 통과.
`A`, `b` 자체는 생성 알고리즘이 같으므로 원소까지 대조한다.

**design** — 앞단 출력(2_primitives)에서 ALIGN 이 고른 variant 를 그대로 배정하면 고정값과
같은 문제(블록 크기·핀·넷)가 나오는가. variant 선택이 성립하는 전제다.

**gpu** — `test/gpu.mjs`: GPU runner 의 calibrate 한 번(W, D, B, lam, mu)이 무차원 CPU
문제와 상대오차 1e-5~1e-7, 600 스텝 뒤 최선 점수가 소수 넷째 자리까지 같고, 끊어
돌린 것이 비트까지 같다. headless Chromium(WebGPU, SwiftShader)에서 돈다 —
Playwright 전역 설치가 필요하다 (`_browser.mjs`). `WEBGPU_NODE` 로 dawn 의 node
바인딩도 쓸 수 있지만 SwiftShader 와의 조합이 이따금 죽는다.

**place / variants** — 앞단 출력만으로 예제 전부를 배치해 겹침 0·대칭 잔차·Order·격자를 검사한다.
수치는 루트 README 의 "배치 결과" 표.

## 겪은 버그 하나 (검사로 남겼다)

화면을 갱신하려고 최적화를 40 스텝씩 끊어 불렀더니 브라우저에서만

`test/chunk.mjs` 가 끊어 돌린 결과와 한 번에 돌린 결과가 같음을 확인한다.

## legalization — MILP 를 LP 로 줄였다

첫 구현은 쌍마다 "왼/오/아래/위" 중 하나를 고르는 이진변수를 두어 MILP 로 풀었다
(11 블록이면 55 쌍 x 4 = 220 개). 브라우저에서 MILP 를 풀려면 solver wasm 을 실어야 한다.

그래서 문제를 줄였다. 연속해가 이미 각 쌍의 방향을 정해놓았으므로 그것을 고정하면
이진변수가 전부 사라지고 LP 만 남는다. 심플렉스 하나(`src/lp.mjs`, 170 줄)면 된다.

**대신 함정이 하나 있었다.** 방향을 "침범량이 가장 작은 쪽"으로 고르면
12 건 중 7 건이 INFEASIBLE 이 됐다. slack 을 1.6 -> 4.0 으로 늘려도 똑같이 7 건이었다 —
공간 문제가 아니었다. 대칭 쌍은 축에 대한 거울이라 세로 대칭이면 cy 가 **항상 정확히
같다**. 그런 쌍에 "위/아래" 분리를 걸면 어떤 theta 로도 만족할 수 없다.
계수행 N[2i]-N[2j] 가 0 이면 그 차이가 상수라는 점을 써서 실현 불가능한 방향을
미리 빼니 12/12 가 풀렸다.

MILP 와 같은 답은 나오지 않는다 (MILP 는 쌍의 관계를 뒤집을 수 있다). 그래서 검사는
값 비교가 아니라 성질로 한다 (`test/legalize.mjs`).

```
예제                        겹침       대칭 잔차   면적    HPWL    LP 실패
telescopic_ota              1.2e-9     3.4e-12    1.00x   1.00x   0/12
five_transistor_ota         0          1.4e-12    1.00x   0.99x   0/12
high_speed_comparator       2.1e-8     7.3e-12    1.00x   1.00x   0/12
cascode_current_mirror_ota  1.1e-8     4.1e-12    0.95x   1.02x   0/12
```

legalize 자체는 12 건에 0.00~0.12 초다. 연속 단계에 비하면 공짜다.
실패(INFEASIBLE)한 후보는 여유 영역을 넓혀 다시 푼다 (1.6 -> 3 -> 6). 성공한 상위 후보는
침범량이 비슷했던 쌍의 방향을 뒤집어 다시 풀어 본다 (`refineDirections`) — 연속해가
나란히 놓은 쌍을 LP 가 못 뒤집는 것을 값싸게 보완한다.

심플렉스는 따로 검증했다: 답을 아는 문제 6 개(최대화/1단계/실행불가능/무한/퇴화/
자유변수 분할) + 무작위 LP 60 건을 꼭짓점 전수 열거와 대조해 최대 상대차 6e-16.

### 배선 격자 — LP 에 정수를 얹었다

배선기는 블록 원점 oX 가 금속 pitch 의 배수여야 받는다 (M1 80, M2 84).
아니면 `Wire to color is offgrid` 로 거부한다.

```
X_i - ax_i = qx * kx_i,   kx_i 정수      (ax = sX * (tx0+tx1)/2)
```

풀고 나서 반올림하면 안 된다 — 대칭이 깨지고 없앴던 겹침이 되살아난다.
LP 라 **다이빙 분기한정**을 붙였다: 완화해의 k 중 가장 분수적인 것을 반올림해
고정하고 다시 푼다. 막히면 반대쪽, 그것도 막히면 한 단계 되짚는다.

**앵커 부호 문제**는 실측으로 풀렸다. ax 는 sX 를 타는데 반전은 legalize 뒤에
정해진다. 그런데 이 PDK 의 템플릿 **59 개 전부** w/2 와 h/2 가 pitch 의 배수라
부호를 곱해도 조건이 같다. sX=+1 로 잡고 `gridOffgrid` 로 결과를 검증한다.

공짜다 — 격자밖 블록이 전부 0 이 되는데 면적과 HPWL 은 그대로다. 격자는 내보낼
후보(최선 + 모양별 최선)에만 건다 — 후보 전부에 걸면 hsc 에서 1 분이 걸렸다.

## 남은 것

- **`Spread` / `Boundary` / `SameTemplate` 제약, `Order` 의 `abut`**: 아직 없다.
- **하위 모듈이 올리는 모양**(`SUB_VARIANTS` 3): hsc 에서 더 나은 모양이 상위에
  오지 못한다. 5 개로 올리면 bbox 가 한 줄 줄지만 배선을 얻고 면적을 내주는 쪽이라 기본을 3 으로 뒀다.
- **실패한 후보의 방향을 뒤집어 살리는 것**: `refineDirections` 는 성공한 후보만 다룬다.
- **variant·반전·영역을 따로 고른다**: variant 는 전역 탐색, 반전은 좌표 고정 후
  좌표하강, 영역은 후보 몇 개. 셋을 같이 푸는 게 원칙적으로는 낫다.
- **WebGPU 를 실제 GPU 에서 재는 것**: 여기는 SwiftShader 뿐이다.
