## 변이 선택 — 기존 방식과 가장 크게 달라진 곳

**요약: 이제 ALIGN 배치기 없이 앞단 출력만으로 배치한다.**
예전에는 블록 크기·핀·영역을 ALIGN 의 place 단계 출력에서 읽었다. 거기엔
ALIGN 이 이미 고른 답이 박혀 있었다. 지금은 `2_primitives` 에서 읽고
**우리가 고른다**.

### 변이가 뭔가

`2_primitives` 는 같은 소자를 여러 종횡비로 만들어 둔다. 트랜지스터도
파라미터도 같고 단위 셀을 몇 열 x 몇 행으로 깔았느냐만 다르다.

```
CMC_PMOS_51983143   X1_Y2    800 x 3528    1열 2행 (홀쭉)
                    X2_Y1   1120 x 2352    2열 1행 (넓적)
DP_NMOS_B_44742353  X1_Y3    800 x 4704
                    X3_Y1   1440 x 2352
```

면적은 비슷한데 **모양이 다르다**. 그래서 장식이 아니라 배치 문제의 일부다 —
홀쭉한 것들을 세로로 쌓는 것과 넓적한 것들을 가로로 붙이는 것은 전혀 다른
레이아웃이고, 영역 종횡비·대칭축 위치·배선길이가 전부 따라 바뀐다.
**연속 최적화로는 못 정하는 이산 선택**이다.

ALIGN 은 이걸 수열쌍 담금질 안에서 좌표와 같이 골랐다 (`sp.selected[block_id]`).
그 배치기는 ILP 솔버가 필요해 브라우저에 못 싣는다.

### 왜 어렵지 않은가 — 세어봤다

| 예제 | 인스턴스 | 변이 조합 |
|---|---|---|
| current_mirror_ota | 5 | **2** |
| five_transistor_ota | 3 | **60** |
| telescopic_ota | 5 | **8** |
| high_speed_comparator | 10 | **4** |
| cascode_current_mirror_ota | 11 | **8** |

블록이 11 개여도 조합은 8 개다. 대부분의 인스턴스는 변이가 하나뿐이다.
**작으면 전수, 크면 추첨**으로 덮을 수 있는 규모다.

### 어떻게 고르나 — 다중 시작에 얹었다

이미 시작점을 수십~수천 개 굴려 점수로 고르고 있으므로, 배정을 그 추첨의
한 축으로 넣으면 끝난다.

```
설정 = (변이 배정) x (영역 후보)
설정마다 A z = b 와 영공간을 새로 만든다   <- 대칭 계가 블록 크기에 의존한다
설정마다 시작점을 batch/설정수 개씩 굴린다
상위 후보를 legalize 하고, legalize 뒤에 다시 점수를 낸다
```

**대칭 쌍은 묶인다.** `SymmetricBlocks` 의 2 원소 쌍은 서로 거울상이라 같은
변이를 써야 한다 — 모양이 다르면 거울이 아니다. 홑원소(자기대칭)는 자유다.
그래서 선택 단위는 블록이 아니라 **그룹**이다 (`variantGroups`).

### `Order` 는 부등식이라 legalize 로 간다

`Order`(블록을 주어진 순서대로 늘어놓기)는 등식이 아니라 부등식이라 영공간
매개화에 못 넣는다. 대신 legalize 가 **이미 쌍마다 분리 방향(왼/오/아래/위)을
고르고 있으므로**, 그 선택을 연속해에서 읽는 대신 제약이 정해주게 하면 된다
(`orderDirections` -> `chooseDirections(.., forced)`). 새 솔버도 새 변수도 없다.

순서는 추이적이라 이웃 쌍만이 아니라 모든 쌍을 박는다. 박은 방향이 실현
불가능하면 조용히 무시하지 않고 `NODIRECTION` 으로 실패시킨다 — 무시하면
제약을 어긴 배치가 그대로 나간다.

`high_speed_comparator` 가 `Order(X_MN0, XDP, XCCN, XCCP, top_to_bottom)` 을
건다. 넣어보니 **위반 0 건, 면적·HPWL 은 그대로**였다 — 연속해가 이미 순서를
지키고 있었다. 숫자는 안 움직였지만 이제 보장된다.
(`abut: true` 는 아직 안 다룬다. 그건 분리 부등식이 아니라 등식이라 영공간 쪽 일이다.)

### 거울 반전(sX, sY)도 같이 고른다

블록은 자기 중심에 대해 뒤집힐 수 있다. 크기는 안 변하고 **핀 위치만** 바뀌므로
영공간도 밀도도 면적도 그대로고 배선길이만 달라진다. 변이와 같은 종류의
이산 선택인데 훨씬 싸다 — 좌표가 정해진 뒤 좌표하강으로 고른다.

자유도는 제약이 정해준다. 세로축 대칭 아래서:

| | x 반전 | y 반전 |
|---|---|---|
| 자기대칭 (홑원소) | 고정 (블록이 이미 x 대칭) | 자유 |
| 거울 쌍 (A, B) | 한 비트, `sX_B = -sX_A` | 한 비트, 둘이 같아야 함 |
| 대칭 밖 블록 | 자유 | 자유 |

효과는 작지 않다 — 실측으로 HPWL 이 **0.66 ~ 0.90 배**로 줄었다.

### 영역은 어디서 오나

place 단계 출력을 안 읽으니 "영역"도 우리가 정해야 한다. 세 군데서 온다.

1. **`AspectRatio` 제약** — 있으면 그게 정답 범위다. cascode 가
   `ratio_low 0.5 / ratio_high 2` 를 건다 (ALIGN 도 이걸 `PlacementCoreAspectRatio_ILP`
   전용 ILP 로 푼다).
2. **구조 힌트** — 두 제약을 함께 본다.
   - `Align h_*` 은 블록을 **가로줄**로 묶는다 (같은 y 선 = 옆으로 늘어선다).
     줄 안에서는 폭이 더해지고 높이는 하나다. 이 줄이 쌓기의 **단위**다.
   - `SymmetricBlocks(V)` 의 홑원소는 중심이 전부 같은 세로축 위에 놓여
     x 로 반드시 겹치므로 y 로 쌓인다: `W >= max`, `H >= sum` — 단, 블록이
     아니라 **단위**를 쌓는다. **거울 쌍은 쌓이지 않는다** (축 좌우로 벌어져
     나란히 설 수 있으므로 폭에만 기여).

   high_speed_comparator 에서 이게 결정적이다. 블록 단위로 쌓던 예전 식은
   2560x25872 (ar 0.099) 를 냈고 ALIGN 은 6080x10584 (ar 0.574) 다 —
   사다리(x1, x2, x4)가 정답에 닿지도 못했다. 줄 단위로 고치니
   **6080x10584 로 정확히 일치**한다.
3. **면적** — 블록 합계 면적 x slack 이상.

힌트의 종횡비에서 출발해 **넓히는 쪽으로만** 사다리(x1, x2, x4)를 놓는다.
힌트는 "다 쌓인다"고 가정하므로 높이는 늘 과대평가, 폭은 과소평가이기 때문이다.

### 계층 설계 — 하위 모듈도 **여러 모양**으로 올린다

`high_speed_comparator` 와 `cascode_current_mirror_ota` 는 최상위가 하위 모듈을
인스턴스로 쓴다. 아래에서 위로 배치한다 — 하위 모듈을 먼저 배치해 크기와 포트
위치를 굳히고(`synthesizeTemplate`), 상위는 그걸 블록 하나로 본다.
굳힌 결과는 `2_primitives/<concrete>.json` 과 **같은 모양**이라 상위 모듈은
leaf 인지 하위 모듈인지 구분하지 않는다. ALIGN 도 같은 순서다.

**하위 모듈을 하나로 굳혀 올리면 상위가 그 모양에 갇힌다.** 실측:

```
모듈                  우리          ALIGN         면적비  종횡비
PRIMITIVE_38447703    2240x5880     3520x3528     1.06x   0.38 vs 1.00
PRIMITIVE_98739713    2240x3528     3520x2352     0.95x   0.63 vs 1.50
PRIMITIVE_8946161     1600x3528     2240x2352     1.07x   0.45 vs 0.95
```

**면적은 이미 ALIGN 급인데 모양이 다르다.** 하위 모듈의 점수에는 종횡비가
없기 때문이다 — 면적과 배선만 본다. 그런데 하위 모듈에서는 모양이 곧 상위의
입력이고, 그게 최상위 구조 하한을 4800x15288 (ar 0.31) 로 만든다
(ALIGN 은 6080x10584, ar 0.57).

고치는 방법은 점수에 종횡비 벌점을 넣는 게 아니라 **고르지 않는 것**이다.
하위 모듈의 점수는 그 모듈 자신의 면적과 내부 배선만 본다 — 상위가 어떻게
쓸지는 **그 자리에서 판단할 수 없다**. 판단할 수 있는 건 상위다. 그러니
고르지 말고 넘겨야 한다. 종횡비별로 몇 개(`subVariants`, 기본 3) 내어 상위의
**변이**로 등록하면 이미 있는 변이 선택 기계가 그대로 고른다. ALIGN 도 같은
구조다 — `PRIMITIVE_38447703_PG0_0` ~ `_PG0_3` 을 만들어 두고 상위가 고른다.

**넘길 때 "좋은 것"을 고르면 안 된다 — "서로 다른 것"을 골라야 한다.**
여기서 두 번 틀렸다.

1. `alternatives` 를 **점수 순으로 잘랐다.** 그러면 종횡비가 한쪽으로 쏠린다.
   `PRIMITIVE_98739713` 의 점수 상위 3 개가 0.63 / 0.27 / 0.37 로 전부 홀쭉했고,
   ALIGN 이 쓰는 1.50 은 4 위라 **상위가 평가할 기회조차 없었다.**
   -> `spreadShapes` 로 종횡비 범위를 고르게 덮는다 (양 끝 + 점수 최선 보장).

2. legalize 를 **연속단계 점수 상위 N 개에만** 돌렸다. 예산이 늘면 후보 풀은
   커지는데 N 은 고정이라 잘 수렴한 것들끼리 몰려 **모양 자체가 줄어든다.**

   ```
   고치기 전   batch  96  모양 후보 6 개  종횡비 0.27~1.50
              batch 288  모양 후보 4 개  종횡비 0.37~1.50   <- 줄어든다
   고친 뒤     batch  96  모양 후보 7 개  종횡비 0.12~1.50
              batch 288  모양 후보 7 개  종횡비 0.14~1.50   <- 유지
   ```

   -> legalize 예산을 **반은 깊이(점수 상위), 반은 너비(설정마다 하나씩)** 로
   나눈다. 모양은 영역 후보가 정하므로 설정을 고루 훑으면 퍼진다.

   너비만 쓰면 반대로 손해다 — 전부 설정 순회로 바꿨더니 평면 설계인
   telescopic_ota 의 HPWL 이 0.987 -> 1.079 로 밀렸다. 거기엔 모양 다양성이
   필요 없고 점수 상위가 밀려나는 손해만 남는다. 반씩 쓰면 둘 다 지킨다.

이걸 고치기 전에는 **예산을 늘릴수록 좋아지지 않았다** — hsc 가
96 -> 1.053, 288 -> 1.000, 864 -> 1.140 으로 널뛰었고 오라클(생성된 후보 중
절대 최선)까지 864 에서 나빠졌다. 샘플을 늘렸는데 오라클이 나빠지려면
후보 집합 자체가 달라진 것뿐이다. 고친 뒤에는 단조롭다:

```
hsc       batch  96  1.053 / 1.333     batch 288  0.965 / 1.192
cascode   batch  96  1.111 / 1.304     batch 288  1.099 / 1.264
```

변이 선택은 여전히 모듈마다 따로 일어난다. 전 계층을 한꺼번에 최적화하지는
않는다 (ALIGN 도 그렇게 하지 않는다) — 다만 하위가 여러 모양을 올리므로
상위가 그중에서 고를 수 있다.


## 앞단 출력만으로 — ALIGN 배치기 없이 (실측)

`node test/place.mjs`. 입력은 `1_topology` + `2_primitives` 뿐이고, 변이·반전·
영역을 전부 우리가 고른다. 기준선은 ALIGN 의 place 결과에서 **직접** 잰다
(고정값 파일이 아니라 — 그건 `<예제>_ours` 를 먼저 읽어서 우리 파이썬 배치기의
좌표가 들어 있을 수 있다).

시작점 96 x 600 반복, 단일 스레드 node.

| 예제 | 블록 | 변이조합 | 면적 | HPWL | 겹침 | 대칭잔차 |
|---|---|---|---|---|---|---|
| telescopic_ota | 5 | 8 | **1.000×** | 0.987× | 0 | 1.1e-13 |
| current_mirror_ota | 5 | 2 | **1.000×** | **1.000×** | 1e-16 | 0 |
| five_transistor_ota | 3 | 60 | **0.862×** | 1.404× | 0 | 0 |
| high_speed_comparator | 10 | 108 | 1.053× | 1.333× | 2e-16 | 9.1e-13 |
| cascode_current_mirror_ota | 11 | 16 | 1.111× | 1.304× | 7e-17 | 0 |

시간은 8 ~ 95 초 (블록 수와 변이 조합 수에 따라).
겹침은 블록 총면적 대비 — 1e-16 은 배정밀도 0 이다.

**아직 ALIGN 에 못 미친다.** 앞의 둘은 bbox 까지 같고, five_transistor 는
면적을 얻고 배선을 내준 맞바꿈이며, 뒤의 둘은 양쪽 다 진다.
그리고 **DRC 는 한 번도 못 봤다** — 격자 스냅과 handoff 가 없어 배선기로
못 넘긴다. 위 수치는 배선 가능성을 말해주지 않는다.

도중 경과 (hsc):

```
시작                    1.316x / 1.826x
점수 정규화 버그 수정     1.140x / 1.459x
하위 모듈 여러 모양       1.053x / 1.333x
```

**telescopic_ota 와 current_mirror_ota 는 bbox 까지 ALIGN 과 정확히 같다**
(1440x11760, 8800x2352). 변이도 반전도 ALIGN 과 같은 것을 독립적으로 찾았다.

`five_transistor_ota` 는 ALIGN 과 다른 변이를 골랐다. 면적을 14% 얻고 배선을
40% 내준 절충이다. 무게를 바꾸고 싶으면 `hpwlWeight` 를 올리면 된다 (재보지는 않았다).

### high_speed_comparator 를 파본 기록 — 짚었던 것이 셋 다 아니었다

처음엔 `Order` 제약을 무시해서라고 짚었다. **틀렸다.** 순서대로 재봤다.

1. `Align` 을 구조 힌트에 반영 -> 하한이 ALIGN bbox 와 정확히 일치 (6080x10584).
2. 그런데 그 종횡비를 **직접 먹였더니 legalize 가 전부 실패**했다. 영역만의
   문제가 아니다.
3. legalize 실패 73/96 을 뜯어보니 방향이 아예 없는 쌍(`NODIRECTION`)은 **0 건**.
   각 쌍은 갈 곳이 있는데 **조합**이 안 맞는다 — MILP 를 LP 로 줄인 대가다.
4. 우리가 배치한 **하위 모듈**이 전부 폭 1280 으로 홀쭉했다. 그게 위층 입력이다.

```
                   우리          ALIGN         면적비
PRIMITIVE_38447703  1280x19992   3520x3528     2.06x
PRIMITIVE_98739713  1280x10584   3520x2352     1.64x
PRIMITIVE_8946161   1280x 5880   2240x2352     1.43x
```

5. 그 모듈을 뜯어보니 **배치는 완벽했다** (블록 2 개가 빈틈없이 나란히,
   채움률 1.00). 틀린 건 **변이 선택**이었고, 원인은 점수 정규화 버그였다
   (아래 "점수 정규화" 절).

고치고 나서 1.316x / 1.826x -> **1.140x / 1.459x**.

6. 그 다음 (3) 을 하려다가 먼저 재봤다. **후보 96 개를 전부 legalize 해서
   절대 최선을 골라도 1.140x / 1.459x — 상위 16 개만 본 것과 똑같았다.**
   legalize 실패는 hsc 의 병목이 아니다. (cascode 는 반대다 — 성공이 11/68 이고
   전수로 보면 합이 2.360 -> 2.327 로 나아진다. 같은 처방이 아니다.)

   병목은 **후보 생성**이었고, 뿌리는 다시 하위 모듈이었다. 면적은 ALIGN 급인데
   모양이 홀쭉해서(ar 0.38 vs 1.00) 최상위 영역 후보가 전부 그 주변에서만 나왔다.
   하위 모듈을 여러 모양으로 올리게 고치니 **1.053x / 1.333x**.

교훈: 원인을 짚었으면 고치기 전에 재라. 여기서 세 번 틀렸다 —
`Order` 도, legalize 실패도, 영역 종횡비도 각각은 사실이었지만 병목이 아니었다.


### 변이 선택이 정말 결과를 가르는가 — 전수로 재봤다

`node test/variants.mjs`. 배정을 전부 돌려 legalize 까지 간 뒤 줄 세운다.
결과가 안 갈리면 고르는 일 자체가 무의미하니, 이게 전제 검사다.

```
five_transistor_ota   변이조합 60, legalize 성공 60/60
   순위  배정        변이           면적비  HPWL비  점수
     1   [2,4,3]     Y1 Y1 Y1       1.077   0.803   1.4742   <- 우리가 고른 것
     2   [2,3,1]     Y1 Y2 Y4       0.923   1.160   1.5261
     3   [2,2,1]     Y1 Y4 Y4       0.862   1.404   1.5530
     6   [2,3,2]     Y1 Y2 Y2       1.000   1.216   1.6979   <- ALIGN 의 선택
    58   [2,0,3]     Y1 Y16 Y1      1.777   7.016   3.8129
    60   [0,0,3]     Y4 Y16 Y1      2.708   5.527   4.2414
```

**최악의 배정은 면적 2.7 배, 배선 5.5 배다.** 같은 트랜지스터, 같은 파라미터,
같은 배치기 — 소자 모양만 바꿨는데 그렇다. 고를 값어치가 있는 선택이다.

telescopic_ota(8 조합)와 current_mirror_ota(2 조합)에서는 **ALIGN 이 고른 것이
1 위**였고 우리도 그것을 골랐다. five_transistor_ota 에서는 ALIGN 의 것이 6 위고,
우리가 고른 1 위가 우리 점수로는 더 낫다 (면적 +7.7%, 배선 -20%).

### 점수 정규화 — 기준은 **배정 전체에 걸쳐 하나**여야 한다

점수는 `면적/refArea + HPWL/refHpwl + 3 x 겹침` 이다. ref 를 1 로 두면 단위가
섞여 (면적 ~1e7, HPWL ~1e4) 면적 항이 통째로 잡아먹는다. 그렇다고 ALIGN 의 답을
기준으로 쓰면 **새 넷리스트에는 그 답이 없다.** 그래서 설계 자신에서 뽑는다.

처음엔 배정마다 **그 배정의** 블록 합계 면적으로 나눴다. 틀렸다.

```
NMOS_4T_85599263   X1_Y16    640 x 19992 = 12.79M
                   X8_Y2    1760 x  3528 =  6.21M     <- 절반
```

같은 소자인데 변이에 따라 블록 면적이 **2 배** 차이난다. 둘 다 빈틈없이 놓으면
채움률 1.0 이라 점수가 같다 — **실리콘을 두 배 쓴다는 걸 점수가 못 본다.**
high_speed_comparator 의 하위 모듈이 전부 홀쭉한 쪽으로 갔고, 그게 위층 입력이
되어 최상위가 망가졌다 (하위 모듈 하나가 1280x19992, ALIGN 은 3520x3528).

telescopic_ota 에서 안 드러난 이유는 그쪽 변이의 면적 차이가 7% 라서다.

```
refArea = min over 배정 (블록 합계 면적)      <- 전체에 걸쳐 하나
refHpwl = sqrt(refArea) x 넷 수
```

**후보 집합의 최소값으로 정규화하는 것도 해봤는데 졌다.** `면적/min(면적) +
HPWL/min(HPWL)` 은 두 항이 1 에서 시작해 대등해 보이지만 최소값이 후보 집합에
상대적이라 같은 맹점이 돌아온다. 계층에서 특히 아프다 — 나쁜 하위 모듈이
위층 입력이 되어 손해가 곱해진다.

```
예제                   상수 기준        최소값 정규화
five_transistor_ota    0.862 / 1.404    1.077 / 0.803
high_speed_comparator  1.140 / 1.459    1.520 / 2.119   <- 크게 진다
```

면적 대 배선의 무게는 `hpwlWeight` 로 빼두었다 (기본 1). 기본값에서 배선 항이
0.5 쯤에서 놀아 면적이 조금 앞선다 — 아날로그에서 면적이 1차 비용이라 그쪽이
맞다고 보고 두었다. 배선을 더 보려면 올리면 된다.

## 검증

**parity** — 파이썬의 `z0`/`N`/`lam`/`mu` 를 그대로 써서 같은 매개화 위에서 대조.
예제 4개(3~11 블록) x 각 3 케이스, 전 항목 기계 정밀도.

```
중심 cx/cy   ~1e-16      배선 W    ~1e-16     밀도 D   ~1e-15
경계 B       ~1e-16      에너지 E  ~1e-16     기울기   ~1e-16
면적 A       ~1e-16      box       ~1e-16     overflow ~1e-16
유한차분 자체검증  ~1e-9
```

영공간 기저는 유일하지 않으므로(같은 부분공간의 아무 정규직교 기저나 된다)
JS 가 스스로 만든 N 은 값이 아니라 성질로 확인한다:
`A(z0 + N theta) = b`(임의 theta), `N^T N = I`, `dim = n - rank`. 전부 통과.
`A`, `b` 자체는 생성 알고리즘이 같으므로 원소까지 대조한다.

## legalization — MILP 를 LP 로 줄였다

파이썬은 쌍마다 "왼/오/아래/위" 중 하나를 고르는 이진변수를 두어 MILP 로 푼다
(11 블록이면 55 쌍 x 4 = 220 개). 브라우저에서 MILP 를 풀려면 solver 가 필요한데,
아티팩트 CSP 는 **라이브러리의 런타임 fetch 를 막는다** — highs-js 가 자기 .wasm 을
못 받아온다. base64 로 박으면 3MB 가 붙는다.

그래서 문제를 줄였다. 연속해가 이미 각 쌍의 방향을 정해놓았으므로 그것을 고정하면
이진변수가 전부 사라지고 LP 만 남는다. 심플렉스 하나(`src/lp.mjs`, 170 줄)면 된다.

**대신 함정이 하나 있었다.** 방향을 "침범량이 가장 작은 쪽"으로 고르면
12 건 중 7 건이 INFEASIBLE 이 됐다. slack 을 1.6 -> 4.0 으로 늘려도 똑같이 7 건이었다 —
공간 문제가 아니었다. 대칭 쌍은 축에 대한 거울이라 세로 대칭이면 cy 가 **항상 정확히
같다**. 그런 쌍에 "위/아래" 분리를 걸면 어떤 theta 로도 만족할 수 없다.
계수행 N[2i]-N[2j] 가 0 이면 그 차이가 상수라는 점을 써서 실현 불가능한 방향을
미리 빼니 12/12 가 풀렸다.

파이썬 MILP 와 같은 답은 나오지 않는다 (MILP 는 쌍의 관계를 뒤집을 수 있다).
그래서 검사는 값 비교가 아니라 성질로 한다.

```
예제                        겹침       대칭 잔차   면적    HPWL    LP 실패
telescopic_ota              1.2e-9     3.4e-12    1.00x   1.00x   0/12
five_transistor_ota         0          1.4e-12    1.00x   0.99x   0/12
high_speed_comparator       2.1e-8     7.3e-12    1.00x   1.00x   0/12
cascode_current_mirror_ota  1.1e-8     4.1e-12    0.95x   1.02x   0/12
```

legalize 자체는 12 건에 0.00~0.12 초다. 연속 단계에 비하면 공짜다.

심플렉스는 따로 검증했다: 답을 아는 문제 6 개(최대화/1단계/실행불가능/무한/퇴화/
자유변수 분할) + 무작위 LP 60 건을 꼭짓점 전수 열거와 대조해 최대 상대차 6e-16.

## 배선 · GDS · DRC — 네이티브 ALIGN 으로 닫았다 (5/5)

배치가 실제로 **배선되고 GDS 가 나오는지**를 확인한 것이다.

```bash
node emit.mjs telescopic_ota              # 배치 -> out/<예제>.place.json
bash ../spikes/route-js.sh telescopic_ota # 덤프에 심고 배선 -> GDS -> DRC
bash ../spikes/drc-sum.sh                 # ALIGN 자신과 나란히
```

| 예제 | GDS | DRC 우리 | DRC ALIGN 자신 |
|---|---|---|---|
| telescopic_ota | 80K | **0** | 0 |
| current_mirror_ota | 80K | 4 | **4 (동일)** |
| five_transistor_ota | 96K | **0** | 0 |
| high_speed_comparator | 172K | **0** | 0 |
| cascode_current_mirror_ota | 204K | **4** | 6 (우리가 적다) |

`current_mirror_ota` 의 4 건은 `DIFFERENT WIDTH` 인데 **ALIGN 자신의 배치에서도
똑같이 4 건** 나온다. SHORT·OPEN 은 양쪽 다 0. 기준선을 같이 재지 않으면
"에러 4건"이 우리 탓인지 알 수 없다 — 한 번 오독해서 시간을 버린 적이 있어
`route-align.sh` 로 같은 조건에서 ALIGN 자신도 돌린다.

### 격자 스냅 — LP 에 정수를 얹었다

배선기는 블록 원점 oX 가 금속 pitch 의 배수여야 받는다 (M1 80, M2 84).
아니면 `Wire to color is offgrid` 로 거부한다.

```
X_i - ax_i = qx * kx_i,   kx_i 정수      (ax = sX * (tx0+tx1)/2)
```

풀고 나서 반올림하면 안 된다 — 대칭이 깨지고 없앴던 겹침이 되살아난다.
파이썬은 MILP 에 정수 변수로 넣었지만 우리는 LP 라 **다이빙 분기한정**을 붙였다:
완화해의 k 중 가장 분수적인 것을 반올림해 고정하고 다시 푼다. 막히면 반대쪽,
그것도 막히면 한 단계 되짚는다.

**앵커 부호 문제**는 실측으로 풀렸다. ax 는 sX 를 타는데 반전은 legalize 뒤에
정해진다. 그런데 이 PDK 의 템플릿 **59 개 전부** w/2 와 h/2 가 pitch 의 배수라
부호를 곱해도 조건이 같다. sX=+1 로 잡고 `gridOffgrid` 로 결과를 검증한다.

공짜다 — 격자밖 블록이 전부 0 이 되는데 면적과 HPWL 은 그대로다:

```
예제                          격자밖        면적          HPWL
telescopic_ota              5 -> 0     1.000 그대로   0.987 그대로
current_mirror_ota          5 -> 0     1.000 그대로   1.000 그대로
five_transistor_ota         3 -> 0     0.862 그대로   1.404 그대로
high_speed_comparator      10 -> 0     1.053 그대로   1.330 그대로
cascode_current_mirror_ota 11 -> 0     1.111 그대로   1.304 -> 1.306
```

### handoff 에서 걸린 것 둘

**(1) 변이가 다르면 leaf 정의가 없다.** 우리는 ALIGN 과 다른 변이를 고를 수
있는데, 그 템플릿의 정의가 덤프의 `leaves` 에 없을 수 있다. 실측으로
`2_primitives/<concrete>.json` 에서 그대로 만들 수 있다 —
`netType == "pin"` 인 터미널만 골라 `netName` -> `name` 으로 옮기면 된다.
그래서 leaves 를 통째로 다시 짠다.

**(2) `__placements_to_run__.json` 이 없다.** `--flow_stop 3_pnr:place` 로 끊으면
`gui` 단계가 쓰는 그 파일이 없어 route 가 `FileNotFoundError` 로 죽는다.
주입기가 같이 써준다.

  메모리는 계측상 문제없어 보인다 — C++ 배선기 본체가 72 MB 고, 8.4 GB 는
  배선 단계가 배치를 다시 돌리던 비용인데 우리 경로엔 그게 없다.
- **`Spread` / `Boundary` 제약, `Order` 의 `abut`**: 아직 없다.
  `SymmetricBlocks`, `Align`, `AspectRatio`(영역 종횡비로), `Order`(abut 제외)
  를 처리한다.
- **설정당 시작점이 1 개로 줄어드는 구간**: `per = floor(batch/configs)` 라
  설정이 batch 보다 많아지면 전부 1 개가 된다. 예산이 늘어도 **깊이는 안 깊어진다**.
  (예산에 따라 결과가 널뛰던 것은 모양 다양성 쪽 버그였고 고쳤다 — 이제
  단조롭다. 남은 건 깊이를 명시적으로 고정하는 것.)
- **legalize 방향 조합**: cascode 는 성공이 11/68 뿐이다. 실패한 것을 그냥
  버리는데, 방향 몇 개를 뒤집어 재시도하면 살릴 수 있다. (hsc 에서는 이게
  병목이 아니었다 — 전수로 풀어도 최선이 같았다. 예제마다 다르다.)
- **WebGPU**: batch 축이 1024 라 컴퓨트 셰이더에 그대로 맞는다.
  지금은 검증된 단일 Objective 를 B 번 도는 구조다 — 정확성이 먼저였다.
- **변이·반전·영역을 따로 고른다**: 변이는 전역 탐색, 반전은 좌표 고정 후
  좌표하강, 영역은 후보 몇 개. 셋을 같이 푸는 게 원칙적으로는 낫다.
